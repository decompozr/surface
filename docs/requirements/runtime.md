# Runtime and surface service requirements

These bounded runtime requirements guide implementation. Architecture documents own detailed mechanisms; evaluation records identify the revisions and scenarios actually tested.

| ID | Observable requirement | Implementation contract and limits |
| --- | --- | --- |
| <a id="r-03"></a>R-03 | Project/surface IDs survive label changes; proven linked worktrees share project identity but retain separate workspace namespaces and domain data. Reject copied/ambiguous identities rather than silently rebinding them. | [Workspace service](../architecture/workspace-service.md#worktree-workflow); Git source merge does not merge databases or reassign pending requests. |
| <a id="r-04"></a>R-04 | Register/add/list/mount/unmount/archive/restore share one operation contract through CLI and MCP. Report source availability, archive state and actual runtime independently. Unmount/archive preserve files and interaction history. | [Project operations](../architecture/project-operations.md); partial/unknown operations require inspection, not assumed rollback. Management UI mutation flows remain unimplemented. |
| <a id="r-05"></a>R-05 | Releases, durable service metadata and project data have distinct owners. Start/status identify the selected running instance; lifecycle operations preserve data and unresolved callback executables. Retirement blocks unresolved accepted/delivering/unknown work without a result. | [Lifecycle](../architecture/lifecycle.md), [installation](../architecture/installation-lifecycle.md), [workspace service](../architecture/workspace-service.md). General future schema migrations, power-loss recovery and indefinite uptime are not established. |
| <a id="r-06"></a>R-06 | Registration, mounting, inspection and restart must not allocate/open project SQLite. Only a valid authorized operation needing storage can acquire it. Release handles on unmount/stop and reopen only on demand. | [Lazy storage](../architecture/installation-lifecycle.md#accepted-project-storage-policy); project backends own schema/transactions and are trusted code, not sandboxed. |
| <a id="r-07"></a>R-07 | Prepare declared source-scoped dependencies; preserve/freeze existing Bun locks, reject unsupported lockfile formats, and report installation/compilation failures. Keep mount diagnostics attributable and neighboring mounts usable within the shared compiler boundary. | [Components](../architecture/components.md), [dependency evidence](../experiments/2026-09-21-dependencies.md), [HMR evidence](../experiments/2026-09-20-scoped-hmr.md). HMR retention is opt-in; arbitrary component state and dependency edits have no transparent migration guarantee. |
| <a id="r-12"></a>R-12 | Source setup uses committed HEAD and the selected home/provider destinations; matching releases are reused or restarted as appropriate. Skills stay symlinked to the checkout, preserving foreign/broken links and directories. Optional private Serve access protects other mappings and reports its actual outcome. | [Setup](../../skills/surface/references/setup.md), [SETUP](../../SETUP.md), [release distribution](../architecture/release-distribution.md). Health, provider discovery, second-device browsing and real delivery are separate gates. No Funnel, implicit home replacement, or automatic MCP-host configuration. |

Interaction requirements R-08–R-11 are in [agent interaction](agent-interaction.md#requirement-index). [Runtime evaluations](../evaluations/runtime-eval.md) map these contracts to existing checks and untested gates.

## Open work and excluded claims

Supported workload size/duration, compiler recreation policy, general service-store migrations, multi-mount backend ownership, project data promotion and fully integrated first-user acceptance remain unresolved. The isolated [multiple-view](../experiments/2026-09-21-multi-surface.md) and [synchronization](../experiments/2026-09-21-surface-sync.md) pilots do not automatically extend the ordinary runtime.

Current setup and distribution are delivered bounded contracts. Older plans naming installation as the next milestone are historical. The missing UI behavior is itemized in [design](../design/README.md), with proposed acceptance criteria distinct from implemented behavior.
