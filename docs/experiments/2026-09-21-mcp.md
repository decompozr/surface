# MCP and CLI interoperability

Date: September 21, 2026. Scope: local executable experiment with a fixture agent adapter, not live session delivery or production MCP packaging.

## Question

Can an MCP client and the singleton CLI operate on the same mounts and interactions without duplicating server state, compilation infrastructure, or delivery semantics?

## Setup

The isolated `experiments/mcp` package pins `@modelcontextprotocol/server` and `@modelcontextprotocol/client` 2.0.0, Zod 4.6.5, TypeScript 6.0.3, and its own Bun lockfile. Official SDK documentation was checked against the installed packages. The adapter uses the SDK's stdio server, tool registration, input validation, and structured output. These are the [official stdio setup](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/get-started/first-server.md) and [tool schema/output conventions](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md).

The adapter reads the existing singleton connection file per operation and forwards to its authenticated HTTP API. The singleton remains the sole owner of mount registration, dependencies, compilation, requests, session binding, deduplication, delivery, and result persistence. The MCP process does not start the singleton or Vite.

The verifier uses a real SDK client connected through a spawned stdio adapter, an actual singleton HTTP server, subprocess CLI calls, a temporary Svelte project, and an explicit fixture adapter. A fixture Unix socket satisfies binding path validation; it is not a Codex control socket. No live agent session is inspected or contacted.

## Observed results

The package TypeScript check and `bun run --cwd experiments/mcp verify` passed.

- `tools/list` advertised all eleven tools with input/output schemas. Invalid namespace syntax, missing required fields, and extra unknown fields were rejected.
- MCP created a namespace and mounted a Svelte component folder. Missing dependencies were prepared. CLI listing observed the same canonical mount; its component page returned HTTP 200.
- A deliberately incompatible Svelte dependency produced a persisted failed mount and an MCP error result, despite an HTTP 200 response. The healthy singleton identity was unchanged.
- MCP created and bound a request; CLI submitted it; MCP published its result; CLI inspected the saved result.
- CLI created another request; MCP submitted it; CLI published its result; MCP inspected the saved result.
- Repeating the same response ID and data did not deliver twice. Conflicting data returned HTTP 409. Closing through CLI prevented a new MCP submission.
- Fixture delivery failures and uncertain outcomes remained distinct `failed` and `unknown` results. Both were MCP errors even with HTTP 200. CLI inspection returned the same state with its existing nonzero exit convention. Neither interface retried delivery automatically.
- CLI unmount was visible through MCP, and MCP remount/unmount was visible through CLI. Server PID and instance ID stayed constant throughout the connected operations.
- Request creation omitted the redundant raw token while retaining its intended private preview URL. Inspect/list outputs did not include the request capability or management token. Management credentials did not appear in the captured MCP stderr.
- An invalid management token was rejected by the real service. A non-loopback connection origin was rejected by the adapter before a request could be sent there.
- With the singleton stopped, MCP tools remained discoverable; a health call returned unavailable and did not start a service. A stale connection produced unavailable for a read and unknown for a mutation.
- Restarting the singleton generated a new connection/instance. The existing MCP connection read that new file and retrieved the earlier persisted result.

The temporary singleton, MCP subprocess, socket, and project were cleaned up. Summary observations and MCP stderr are retained locally in ignored `.artifact/mcp-proof/` rather than committed as portable evidence.

## Contract and limitations

The thin adapter preserves HTTP outcomes instead of treating transport acceptance as completion. A mutation whose HTTP response is lost cannot safely be declared unexecuted. It is reported as unknown without automatic retries. SDK schema-validation errors are the SDK's normal error results; they do not use the adapter's structured status envelope because its handler is never called.

The management credential stays in the connection file and request header. Request creation must return a browser capability to make its page usable, so its private preview URL is an intentional capability disclosure to the calling agent/host. That URL must not be placed in public documentation. Read tools do not repeat it. The host has management privileges; namespace strings and tool annotations are not security boundaries.

This proves protocol discovery, execution, and shared-state interoperability. It does not prove setup in a particular desktop host, remote OAuth, streaming HTTP, multiuser authorization, automatic service installation, or another live model round trip. The existing singleton's framework, HMR, origin-trust, and dependency limitations still apply. An HTTP component response in this suite is not a new visual browser or HMR verification.

## Reproduce

From a checkout with the root and singleton dependencies installed:

```sh
bun install --cwd experiments/mcp --frozen-lockfile
bun run --cwd experiments/mcp check
bun run --cwd experiments/mcp verify
```

See the [adapter README](legacy-mcp-package.md) for the invocation and tool list. The fixture suite can run alongside other experiments because it uses its own temporary state, loopback port, source folder, and socket.
