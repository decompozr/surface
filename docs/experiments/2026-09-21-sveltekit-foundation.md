# SvelteKit singleton application foundation

Date: September 21, 2026 (America/Toronto).

Status: the bounded foundation experiment passed its type check, application build, and Chrome/runtime verification. SvelteKit is a viable application-shell candidate for the observed workflow. This does not by itself adopt the architecture or establish production readiness.

## Question and implementation

Can SvelteKit provide application routes, a management overview, and an API while retaining one process/listener/live compiler for runtime-mounted Svelte components?

The experiment builds one SvelteKit shell using adapter-node and imports its generated `handler.js` into the existing singleton. The singleton dispatches selected application paths to that handler after its host/origin guards and authenticated core API handling. Other routes retain the existing component catalogs, generated CSR entries, scoped interaction API, and Vite middleware. Mounting does not launch another Kit application or Vite server.

The shell provides a server-rendered `/manage` overview and a read-only `/kit-api/status` endpoint. The wrapper supplies the state-directory identity on the server-side request; Kit's hook places it in request locals for server-only registry reads. No process-global state-directory setting or browser management-token relay is needed. Mutations remain on the existing authenticated API/CLI, so this is not yet a complete management GUI.

Pinned versions: SvelteKit 2.70.3, adapter-node 5.5.7, Svelte 5.57.1, Vite 8.3.0, vite-plugin-svelte 7.3.0, svelte-check 4.7.6, TypeScript 6.0.3, and Bun 1.4.0.

## Observations

| Gate | Observed result |
| --- | --- |
| Application shell before mounts | Chrome rendered the built Kit overview with an empty catalog. The status endpoint reported the same process ID. |
| Mount after application startup | Two namespaces gained project-owned component folders without restarting the application or replacing its Vite instance. |
| Source-specific dependencies | The mounted browsers executed nanoid 4.0.2 and 5.1.5; recorded module URLs pointed to their separate source `node_modules` trees. |
| HMR and unsent draft | A compatible component edit retained an opted-in draft and the original document marker. |
| Compile failure and recovery | Alpha displayed its scoped diagnostic and recovered with the draft intact. Beta submitted successfully and retained its document while the Kit overview remained usable. |
| Shared interaction core | Custom data reached the exact fixture binding. The actual singleton result CLI published the outcome, Chrome displayed it, and reload restored it without resubmission. |
| Authorization and data minimization | Kit HTML/status omitted management/request tokens, source roots, binding/session IDs, and socket paths. Management authentication, cross-mount request scope, host, and origin checks remained enforced. |
| Registry diagnostics | A missing initial registry produced an empty catalog; malformed registry JSON returned 500 instead of a healthy empty result. |
| Unmount and remount | The selected preview became unavailable; Kit status reflected unmounted/ready phases; remount plus reload restored the original interaction. |
| Singleton topology | `lsof -nP` observed exactly one TCP listener, the Kit endpoint reported the singleton PID, and the retained Vite object had no independent HTTP server. |

Inputs and adapter replies were explicitly automated fixtures. This run did not contact a live model session and does not add a new live `start`/`steer` claim. Earlier live delivery evidence remains separate. Nor does an automated form submission imply that the user selected its values.

The management, retained-draft, and roundtrip screenshots plus machine-readable observations are saved locally under ignored `.artifact/sveltekit-proof/`. Management and result screenshots were visually inspected. The result screenshot follows a full reload: its blank draft demonstrates the preview-session reset, while the persisted result remains visible. ## Build/runtime boundary

The Kit shell has a real successful application build. Its routes and management UI are prebuilt; updating that shell requires rebuilding and restarting the wrapper. The runtime still retains a development compiler and watcher for component folders that were unknown at shell build time. A successful Kit build does not turn arbitrary future mounts into production bundles.

Mounted components use CSR generated by the existing host. The management page's SSR does not establish SSR for mounted project code. Independent Svelte compiler versions, arbitrary SvelteKit project configs/routes, and server execution of mounted code remain outside this experiment. The shared compiler/process/browser origin remains a trusted-code boundary, not a namespace sandbox.

## Findings affecting reproduction

- Worktree dependencies must resolve inside the allowed compiler installation. Linking the worktree's singleton `node_modules` to another checkout made Vite reject framework module realpaths with 403; a worktree-local frozen install corrected that environment setup.
- After unmount, a preview can legitimately display its unavailable response. Revisiting the same capability-fragment URL may be a same-document navigation, yielding no new HTTP request. The verifier waits for unmount navigation and explicitly reloads after remounting.
- Listener inspection uses numeric `lsof -nP` output; hostname resolution otherwise represents `127.0.0.1` as `localhost` without indicating another listener.

The separate dependency/lifecycle experiment identified an existing unmount reload-scope issue and provides a targeted event fix. This foundation record's neighboring-preview guarantee covers source errors/HMR; the combined integration check must retain that lifecycle fix before claiming unmount leaves unrelated documents untouched.

## Reproduce

Follow [the package guide](../../experiments/sveltekit/README.md) to install, check, build, and run:

```sh
bun run --cwd experiments/sveltekit check
bun run --cwd experiments/sveltekit build
bun experiments/sveltekit/verify.ts
```

The check returned zero errors and warnings. The built handler ran successfully under Bun in the browser experiment. Injected malformed registry and Svelte syntax errors intentionally print diagnostics; they are expected verification cases. Temporary resources were cleaned up.

## Recommendation

Proceed with SvelteKit as a candidate for the actual server's application shell while retaining a separately defined runtime compilation service inside the same singleton. Its routing and server-only load/API code worked with dynamically registered CSR component folders. Before adoption, integrate the dependency/lifecycle changes and preserve the same browser and authorization checks. A complete management UI, durable service packaging, mounted SSR, and untrusted-code isolation require their own scope and evidence.
